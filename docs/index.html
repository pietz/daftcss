Frequently asked
Does it need a build step?

No. Drop one stylesheet into your <head> and your HTML starts looking like this page. The framework was built (LightningCSS), but consumers don't run anything.

Can I use Daft with React, Vue, Svelte, or Next?

Yes. Daft styles raw HTML — anything that renders <button>, <input>, <table> works. No component wrappers, no framework adapters, no JS runtime to integrate.

How do I customize it?

Override CSS variables at :root, or scope them to any element. Ten core tokens cover the whole system — color, radius, spacing, font scale. The Override card at the top of this section is a working example.

How is Daft different from Pico.css?

Same idea — style plain HTML without classes. Daft pushes the visual finish toward shadcn-grade defaults and adds modern primitives Pico predates: light-dark() theming, OKLCH palettes, the native Popover API, container queries on slides.

When should I not use Daft?

When you need pixel-precise marketing pages or a heavily custom design system. Daft is for products that benefit from sensible, consistent defaults — not for landing pages that have to look like nothing else.

What if I need a component Daft doesn't have?

Write your own using Daft's tokens (--primary, --radius, --spacing, --border). It'll inherit palette and theme changes automatically — your custom component themes itself.

Can coding agents write Daft well?

Yes. Semantic HTML is already in every model's training data — Pico and other class-less frameworks normalized the pattern years ago. Daft also ships an official Claude Code skill, so agents pick up the idioms and class names without you pasting docs into context.

Which browsers are supported?

Chrome 123+, Firefox 129+, Safari 18+. Daft relies on light-dark(), OKLCH, CSS nesting, color-mix(), the Popover API, and @starting-style — all of which shipped together in early 2024.

Theme tokens

One variable. Every component.

Daft tokens cascade in three layers. Set a handful at the root and the rest of the system — every spacing step, every radius, every component state — recomputes from them.

Core set at :root

A small set of variables defines the shape of the system.

--spacing:         1rem;
--radius:          0.5rem;
--font-scale:      1.25;
--component-height: 2.5rem;
Derived via calc()

Every step on every scale recomputes from the core.

--spacing-xs: calc(var(--spacing) / 4);
--radius-sm:  calc(var(--radius)  / 2);
--text-lg:    calc(var(--text-base)
              * var(--font-scale));
Semantic light-dark()

Surfaces and brand follow color-scheme on their own.

--background: light-dark(…, …);
--foreground: light-dark(…, …);
--primary:    light-dark(…, …);
--border:     light-dark(…, …);

For coding agents

Cheap to generate, hard to drift on.

Daft is the same framework whether a human or a coding agent writes the HTML. Two side effects of "no classes needed" matter more when the writer is a model.

Fewer tokens per element ~3 vs ~50

A Daft button is <button>. A Tailwind button is nine utility classes the agent regenerates from working memory on every page. Across a real codebase the difference is measurable.

Nothing to drift on

The theme lives at the root in roughly ten variables. Generated pages share the same radius, spacing, color, and focus states because there is structurally no surface for an agent to invent variations on.

No design system to feed in

Semantic HTML is already in the model's training data. There is no component API to paste into context, no class vocabulary to keep in working memory, no design-system docs to keep updated.

What we kept from others

We picked the parts we liked.

Three honest comparisons against the libraries Daft borrowed from. Same goals, different trade-offs.

vs Tailwind

One render, two ways to write it.

Daft borrows Tailwind's discipline around design tokens, color, and responsive primitives. What changes is the markup. Same button, both styles below.

Daft

<button>
  Save changes
</button>

Tailwind

<button class="inline-flex
  items-center justify-center
  rounded-md text-sm font-medium
  transition-colors
  disabled:opacity-50
  bg-primary
  text-primary-foreground
  hover:bg-primary/90
  h-10 px-4 py-2">
  Save changes
</button>

vs Pico.css

Same idea, a sharper finish.

Pico opened the door: style plain HTML without classes. Daft keeps that idea and pushes the visual finish toward shadcn-grade defaults — same markup, sharper outcome.

vs daisyUI

Smaller than the plugin you'd add to Tailwind.

daisyUI shares Daft's preference for readable class names over utility soup. The trade-off is the dependency: daisyUI is a Tailwind plugin, so the shipped bundle stacks on top of Tailwind. Daft is the single file you link.

Slides

HTML has a presentation mode.
